# 在糯叽机直接接收相机图片

[返回首页](../README.md) · 上一步：[设备联网](02-device.md)

这是当前推荐路线。StackChan拍照，将JPEG上传到VPS；网关把照片作为MCP图片内容返回；糯叽机再把图片交给当前支持图片输入的聊天模型。

```text
聊天角色调用 take_photo
        ↓
StackChan 拍一张新照片 → VPS接收JPEG
        ↓
MCP返回图片 → 糯叽机当前聊天模型识图并回答
```

它仍然只占一次工具调用，不另调备用的 `take_photo_and_analyze`。直接传图不会额外调用那个备用识图中转站，但当前聊天模型处理图片仍可能计费。

## 1. 添加 MCP 服务

**位置：糯叽机的 MCP 配置页。**

| 字段 | 填写内容 |
| --- | --- |
| 名称 | 自己能认出的名称，例如 StackChan |
| 连接类型 |  MCP标准|
| 服务URL | `https://mcp.example.com/mcp`，替换实际域名 |
|  身份验证| Bearer / 令牌，填VPS的 `STACKCHAN_TOKEN` |

勾选启用此服务，启用这台MCP服务，并在当前角色中允许使用。客户端字段名、刷新入口可能更新，不要求与表格逐字一致。

角色工具列表不会固定永远是53个：上游版本和你安装的扩展会改变数量。重点检查 `get_status`、`take_photo`、`set_avatar`、`set_blink` 等是否存在。`show_text`在个人环境是额外修改，见下一章。

## 2. 先验证设备在线

在聊天里发：

> 请只调用 StackChan 的 get_status，告诉我设备当前是否已连接。不要调用其他工具。

查看实际返回的状态字段，而不是只信角色口头说“连接了”。如果没有设备连接，先回设备章或排错章，不反复调用相机。

## 3. 确认当前聊天模型支持图片输入

客户端支持MCP图片结果和模型本身支持图片输入是两件事。文字模型不会因为接入相机就突然获得识图能力。若使用中转站，还要确认该模型在那条实际通道中支持图片，不只看模型名称。

个人测试中，同一套既有工具无需再新增一个“传图片工具”；0.18.0对应代码已经有 `_photo_contents`，会读取照片并生成MCP图片块。当前本地代码限制内联JPEG最多200KiB；客户端、模型可能另有限制，不把这200KiB当成所有版本的统一上限。

## 4. 拍一张容易验证的新照片

移开遮挡，对准具有明确颜色或文字的物品，例如一瓶水。不要把你希望模型猜出的答案先写进问题里。

在糯叽机发送：

> 请只调用 StackChan 的 take_photo，question="请查看这次拍摄的图片，描述画面中的物品和颜色。" 根据工具返回的图片回答；如果没有收到可读取的图片，请明确说明。不要调用 take_photo_and_analyze 或其他工具。


## 5. 什么输出算验证成功

检查三件事：

1. 实际调用的是 `take_photo`。
2. 返回不仅有 `image_path`、`size_bytes`，还附带图片；个人客户端显示过 `[image #1 returned by this tool — attached as a picture]`。
3. 角色描述了这张新照片里的具体信息，与现实物品一致。


## 6. 如果仍然看不到图片

- 只有路径或 `[image content omitted]`：只能证明某一层没有把图片显示出来，不能单独判定是相机没拍成；核对客户端版本、实际返回内容与模型支持。
- 返回 `Failed to connect to explain URL`：设备连接照片上传地址失败，未到识图阶段；去[排错章](troubleshooting.md)。
- 角色只说“拍好了”但不描述：检查工具返回图片和聊天模型，不把角色口头回复当成已经看图的证明。
- 第一次失败不要连点多次。先看日志，避免重复拍照、重复处理图片和额外用量。

直接看图已成功后，主路线不需要外部视觉模型的API Key，也不依赖其他项目。可以保留备用工具，但在人设中让直接看图优先。
